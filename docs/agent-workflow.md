# 代码工作方式

本文件记录在本仓库工作中反复踩到的坑与对应的做法。不写通用套话，每条都来自实际返工。

## 先读后写

写第一行代码之前，把要调用的函数真正读一遍：签名、抛什么异常、读的是哪份状态。

断言一个函数「大概是这样」然后边写边试，代价是成倍返工。真实例子：给预瞄线加冻结逻辑时没读 `FishingRules.Range` 的实现，写完后才发现它内部是

```csharp
Equipped(s, p)?.Range ?? 0   // 内部是 First(i => i.Id == p.EquippedRod ...)
```

按 id 去背包里查鱼竿，查不到就抛异常。如果一开始读了这一行，就不会把「预测态玩家」传进去——预测态可能已换上尚未确认的鱼竿，那一刻查不到。读它花了不到一分钟，返工花了三轮。

**具体做法**：涉及状态读取、可能抛异常、有副作用的调用，先看实现再动笔。纯机械的 getter 可以跳过。

## 分清时间线：确认态还是预测态

客户端有能力预测时，同一份数据有两个版本，来源不同、新鲜度不同：

- **确认态**（`InspectState()` / `state`）：服务器已核对，落后约一个来回。
- **预测态**（`InspectPredictedState()` / `predicted`）：本地已推算，即时，但可能被回滚。

同一个改动里，两者往往都要用，而且用哪个必须逐项判断。上次三个 bug 里有两个是这个：

| 判断什么 | 读哪个 | 为什么 |
|---|---|---|
| 本地玩家现在能不能出钩 | 预测态 | 用确认态会滞后约一秒，操作反馈是错的 |
| 当前手长（射程） | 确认态 | 预测态可能含未确认的装备，按 id 查表会失败 |

**具体做法**：写下每一处状态读取的理由。同一函数里混用两种状态时，注释说明哪处用哪个、为什么——否则下一个改的人会顺手统一成一种，然后踩回同一个坑。

## 验证成本匹配改动半径

不是所有改动都值得跑全量测试。按影响面选验证手段，并且**明确说出跳过了什么**：

| 改动范围 | 验证手段 |
|---|---|
| 只改表现层（渲染、UI 布局、颜色），不产生网络字节，不碰确定性状态 | 编译通过即可 |
| 改模拟规则、状态编码、协议 | 对应单测 + 四客户端一致性 |
| 改传输、重连、存档事务 | 全量 `./scripts/verify.sh` |

判断依据是「会不会改变别人算出来的状态」，不是「改了行数多不多」。改一个 `LineRenderer` 的位置不会影响任何人的哈希，跑 15 分钟真实 UDP 全量测试只会拖慢反馈。

**具体做法**：编译验证完成后，说明「只做了编译验证，因为这次改动不进入确定性状态；需要的话可以跑全量」。把选择权交出去，而不是默默跑完。

## 一次只处理一个请求

上一个任务的工具链不要带进下一个任务。为了验证一张时序图去装 mermaid-cli，是那个任务的事；如果它还没装好又开了新任务，会同时拖住两件事。

**具体做法**：新请求开始时确认手上没有遗留的后台任务或半成品，有就收尾或明确搁置。

## 改到第三遍就停下重读

连续三次补丁式修改，说明对系统的理解模型本身就是错的，继续打补丁只会在错的模型上叠加更多补丁。

**具体做法**：第三次返工时停下来，把相关调用链完整读一遍，确认模型，再一次性改对。而不是继续逐个试。

## 只在影响方案形状时才问

不确定的交互要问，但只问那些会改变实现结构的问题。

反例：问「预瞄线冻结后圆环要不要跟着角色走」——这不是细节，因为两种实现的代码结构完全不同，问对了能省掉整轮返工。

正例：不问「圆环用 0.42 还是 0.45 半径」——这种改一行就调，问了只是打断对方。

## 交付时说清验证边界

区分三件事，不要混成一句「已完成」：

- **验证过的**：编译通过、哪些测试通过、实际渲染/运行结果。
- **没验证的**：实机手感、视觉观感、未覆盖的分支。
- **推断的**：读代码得出但没运行的结论。

「编译通过 + 既有测试未回归」不等于「功能正确」。表现层改动尤其如此——代码能编译，但冻结时机差一帧、圆环偏大偏小，只有跑起来才知道。
