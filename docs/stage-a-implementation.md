# 阶段 A：实现与使用说明

日期：2026-10-10。实现范围是“给定完整输入，稳定地算一帧，并能保存、恢复、重放”。该段描述阶段 A 当时的范围。2026-10-15 已在其上接入 B～E，当前成员、预测和正式存档接口见 [C/D 实现说明](stage-c-d-implementation.md)。

## 1. 已有模块

| 模块 | 做什么 | 入口 |
| --- | --- | --- |
| 接入接口 | 让不同游戏提供自己的计算规则和状态 | `SimulationModule<TState>` |
| 帧驱动 | 验证输入，再按固定顺序计算一帧 | `SimulationRunner<TState>.Advance` |
| 检查点 | 保存一帧结束后的完整状态 | `CaptureCheckpoint`、`Restore` |
| 状态编码 | 把检查点变成可保存、可比较的字节 | `CheckpointCodec` |
| 输入录制 | 保留初始检查点和连续输入，有数量与字节上限 | `ReplayRecorder` |
| 输入重放 | 恢复起点，重新执行每一帧输入 | `ReplayPlayer`、`ReplayCodec` |
| 控制台验收 | 用两个不同模型检查结果，导出验证文件 | `HeadlessHarness` |

工程引用关系及运行命令见 [项目 README](../README.md)。`FrameSync.Runtime` 只引用 `FrameSync.Abstractions`，两个示例也只依赖接口工程。`framework/FrameSync.sln` 不包含示例和控制台工具。

## 2. 游戏要提供什么

`SimulationModule<TState>` 把以下实现组合起来；`TState` 是游戏自己的完整状态类型，框架不知道它的字段。

| 接口/方法 | 通俗说明 | 必须遵守的约定 |
| --- | --- | --- |
| `ISimulationFactory.Create` | 创建一份独立的游戏计算实例 | 不能返回旧实例，实例之间不能共享可变世界或随机状态 |
| `Initialize` | 使用参与者和初始化数据准备实例 | 不读取 Unity、设备、系统时间，不访问文件和网络 |
| `Step` | 输入相同，推进一帧后结果相同 | 不做音效、成就、写存档等外部操作；需要通知外部时返回事件数据 |
| `Capture` | 拿到当前全部状态 | 包含影响后续计算的所有数据，包括随机数进度；不能暴露仍在修改的对象 |
| `Restore` | 把保存状态完整装回当前实例 | 不保留可变外部引用，不能漏掉字段 |
| `IStateCodec.Encode/Decode` | 游戏状态与字节互转 | 固定字段顺序、整数宽度、字节序；拒绝无效值和多余字节；解码结果必须独立 |
| `IInputValidator.ValidateCanonical` | 判断输入是否是规定的格式 | 无副作用，不依赖当前世界；业务上的“能否执行”由 Step 判断 |

`CompatibilityManifest` 是兼容清单，包含游戏标识、规则版本、输入版本、状态版本、内容摘要、确定性算法摘要。这里的字符串由接入方维护，框架不会自动识别规则代码发生了哪些变化。恢复时必须完全匹配。

“确定性”表示同样的起点和输入得到同样的结果。框架保证输入顺序和恢复流程，接入方仍要保证规则本身确定：避免平台相关浮点物理、未排序集合遍历、系统随机数和异步结果进入计算。本阶段没有通用物理引擎或定点数学库。

状态编码器、输入验证器和实例工厂可以共用一个无状态对象；可变游戏数据必须留在工厂创建的实例里。

## 3. 一帧怎样运行

1. 调用者准备 `InputFrame`，包含本会话每位参与者的一个输入。
2. 构造时复制输入字节，按 `Slot` 排序；重复位置直接拒绝。
3. `Advance` 核对会话、运行编号、帧号、控制权编号、输入长度和输入格式。
4. 把按顺序排列的 `SimulationInput` 交给游戏，计算一次 `Step`。
5. 检查事件数量与长度，记录输入历史和缺失次数，最后提交帧号。

几个容易混淆的编号：

| 名称 | 含义 |
| --- | --- |
| `SessionId` | 这次会话的身份 |
| `Epoch` | 会话中的运行编号，用来拒绝旧运行消息 |
| `Tick` | 本次运行的帧号，初始为 0，第一次输入为 1 |
| `BaseTick + Tick` | 累计帧号，用于以后从存档重新开局 |
| `ParticipantId` | 参与者的稳定身份 |
| `Slot` | 本次运行中分配的位置，决定输入排序 |
| `Generation` | 这个位置的控制权编号，用来拒绝旧控制者输入 |

初始身份名单固定，当前已支持名单内的激活、停用与控制代数转换。初始支持 1～4 位参与者，默认最多 4 位；人数限制可以配置，超过四人的运行效果尚未验证。

逻辑时间是每帧精确的 `1 / TickRate` 秒。框架不按现实时间自动推进，所以控制台可以快速计算 10 万帧。以后调度模块负责“什么时候调用 Advance”。

`InputOrigin` 只记录输入是实际提交还是外部补齐。游戏只收到输入内容，不收到来源标记。阶段 A 不决定补输入策略；它的控制台人为提供少量补齐记录，用来验证缺失计数也能恢复。阶段 B 的会话层现已能用游戏提供的中性输入补齐，见 [阶段 B 实现说明](stage-b-implementation.md)。

一个运行实例由同一线程拥有；并发调用不受支持。运行时拒绝重入。格式、编号或长度错误在计算之前拒绝；游戏计算中途抛异常或输出事件超限时，实例进入故障状态，必须显式恢复有效检查点后才能继续。

## 4. 状态保存与恢复

`S[f]` 是执行完第 f 帧后的状态。捕获检查点时保存：

- 兼容清单、会话与固定成员表、运行限制、累计帧基础值和当前帧号。
- 有限的近期输入及来源、每个参与者的连续缺失次数。
- 初始化数据，以及由游戏编码的完整状态字节。

`ByteString` 持有自己的字节副本；`ToArray()` 返回另一个副本。检查点及录制暴露只读集合，因此修改原始输入数组或导出的数组，不会改掉已经保存的记录。

恢复采用“先准备新实例，再替换旧实例”：

1. 检查兼容清单、会话成员、运行限制和历史输入。
2. 解码游戏状态，再编码一次，要求字节完全相同。
3. 工厂创建新实例，用检查点里的初始化数据初始化，再恢复游戏状态。
4. 再捕获一次状态，确认每个字节都恢复完整。
5. 全部成功，才替换当前模拟、输入历史、计数和帧号。

任何步骤失败，当前实例保持原样。这保证恢复过程不会把正在运行的世界改成半份旧状态；游戏接口自身必须遵守无外部副作用的约定。

如果某个游戏要求非空初始化参数，创建用于加载的运行实例时，应传入 `checkpoint.InitializationData`。恢复属于同一个会话；当前“读档后创建新房间”使用 `CheckpointRestart.Create` 做独立的身份转换。

`InspectState()` 通过编码再解码提供独立副本，适合当前验收与调试；每帧渲染大量实体时需要后续专用读取接口，不能把此方法当作已经优化的渲染路径。

## 5. 编码格式与大小限制

当前格式版本都是 **1**。除 Guid 外，多字节整数一律小端；Guid 固定使用 .NET `Guid.ToByteArray()` 的 16 字节排列。文本为严格 UTF-8，前面写入 32 位无符号字节长度。接入方不能直接使用平台内存布局或对象序列化来代替这些约定。

检查点布局：

```text
FSCP 标识（4） + 格式版本（2）
兼容清单（6 段带长度文本）
SessionId（16） + Epoch（8） + TickRate（4） + BaseTick（8） + Tick（8）
6 个运行限制（各 4 字节）
成员数量（2） + 成员表〔Slot（2）、ParticipantId（16）、Generation（8）〕
每位成员的连续缺失次数（各 8）
历史帧数量（4） + 按帧排序的输入记录
初始化数据长度（4） + 初始化数据
游戏状态长度（4） + 游戏状态
此前全部字节的 SHA-256（32）
```

每条输入帧：`Tick(8) + 输入数(2)`，随后每条输入为 `Slot(2) + Generation(8) + Origin(1) + PayloadLength(4) + Payload`。

录制布局：`FSRP(4) + 版本(2) + 初始检查点长度(4) + 完整检查点 + 帧数量(4) + 连续输入帧 + SHA-256(32)`。录制帧必须紧接初始检查点，不能留洞或重复。

SHA-256 用于发现字节损坏和比较状态，不能证明发送者身份。网络认证属于后续通信层。

| 限制 | 默认值 | 达到限制后的行为 |
| --- | --- | --- |
| 参与者 | 4 | 拒绝创建/加载 |
| 每位参与者每帧输入 | 128 字节 | 拒绝输入 |
| 单个完整检查点 | 8 MiB | 拒绝捕获/加载，不只检查游戏状态长度 |
| 近期输入历史 | 128 帧，可调为 1～128 | 按帧淘汰最早记录 |
| 每帧事件 | 128 条，每条 1024 字节 | 游戏输出超限则进入故障状态 |
| 单份录制 | 100000 帧、64 MiB | 拒绝继续追加/加载，不偷偷删除起点 |

解码先检查总字节上限和摘要，再检查内部长度、帧顺序、成员与缺失计数。核心限制的是编码和框架持有的数据；游戏自己的 `Step`、`Capture`、`Decode` 仍需限制内存使用。控制台读取文件也先检查文件大小，再分配读取缓冲区。

## 6. 重放和外部事件

`ReplayRecorder` 是有限录制容器，成功 `Advance` 后才能 `Append`。它不负责调用游戏；如果业务要把录制用作必不可少的日志，需要在到达容量前轮换并协调推进，不能忽略追加失败。

`ReplayPlayer.Play` 恢复录制起点，然后执行全部输入，最后返回检查点。中途遇到非法输入会抛异常，调用者应把这次重放视为失败；它不保证整段重放失败时自动退回调用前的状态。

`Step` 返回的事件有稳定标识：会话、运行、帧号、帧内序号。当前重放会重新计算事件，但不会自动播放音效、写成就或执行文件操作。当前会话层已提供预测事件撤销和确认事件去重；直接调用运行器时，不能把每次重算的事件用于不可逆操作。

## 7. 怎样证明当前实现能用

`./scripts/verify.sh` 执行以下检查：

1. 仅构建核心解决方案并运行核心测试，不依赖任何示例。
2. 测试两个示例的手算结果、随机数进度恢复、输入拒绝及命令行失败路径。
3. 两模型分别运行 100000 帧，每 30 帧保存摘要，末帧也保存摘要。
4. 从第 0、1、33333、50000、99999、100000 帧的检查点恢复，重放剩余输入；核对周期状态摘要、每帧事件摘要和完整最终状态字节。
5. 将录制写入文件，启动新进程重放，核对最终摘要。

导出目录 `artifacts/stage-a` 中的 `.fsrp` 是输入录制，`.fscp` 是最终检查点，`.sha256` 是预期最终摘要；`report.json` 包含周期摘要和恢复次数，另有两个新进程的报告。这些是诊断文件；正式存档已由 Persistence 与 FileSystem 工程提供原子保存，备份策略仍待后续。

2026-10-10 的 macOS arm64 最终验证结果：35 项核心测试、13 项示例/命令行测试通过，其中覆盖 1～4 位参与者的推进和恢复。两个模型均通过 10 万帧和新进程重放，每个模型在不同进程得到的 3334 个周期摘要全部一致。构建为 0 警告、0 错误。执行日志在 `artifacts/stage-a/verification.log`。固定输入与当前格式的最终摘要：

```text
counter  f405e61e8313941177888b2f9e069ee72db08dd0f8e4bebd4a1a939d1b5f00ab
grid     ba257114141f1e3edbb4e17c2a049c8594edf3b5189910feefb12c0533544724
```

Windows 尚未实测。应把相同录制复制到 Windows，运行 `--replay ... --expected-hash ... --report ...`，比较对应帧的 `PeriodicHashes`；构建通过不能代替跨系统确定性验证。当前也没有运行 Unity 编辑器或 IL2CPP 验证。

一次独立代码审查发现两个边界问题，均已用先失败后通过的测试修复：解码现在拒绝超过内部声明上限的检查点；报告路径与导出文件重名时，在写任何文件之前拒绝。完整实施记录见 [阶段 A 执行记录](superpowers/plans/stage-a-progress.md)。

## 8. 下一阶段如何接上

阶段 B 增加输入收集、截止时间、缺失输入策略、成员事件与内存通信，让服务器和多个客户端分别持有 `SimulationRunner`。阶段 A 的完整状态、稳定身份、有限历史和规范编码继续使用。

当前阶段 C 已增加预测输入和自动选择恢复点，复用 `Restore + Advance`；阶段 D 已基于检查点实现可靠文件保存和读档重开；阶段 E 已接入独立 UDP。中途加入和断线恢复的协调流程仍按原范围后置。

阶段 A 实现时只定义实际使用的接口，没有提前加入空的服务器、客户端或传输实现。2026-10-13 起，阶段 B 已增加有实际行为与测试的会话和传输库，见 [阶段 B 实现说明](stage-b-implementation.md)。更完整的目标接口仍以 [核心技术方案](superpowers/specs/2026-10-10-frame-sync-core-design.md) 为设计依据，已实现接口以本说明和源码为准。
