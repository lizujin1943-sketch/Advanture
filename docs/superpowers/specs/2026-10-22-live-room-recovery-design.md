# 晚加入与断线恢复设计

2026-10-22。依据主设计的联机状态、耐力恢复、落水救援和重复结算约束，继续“实现已描述但未落地玩法”的总目标。一次独立 builder check 已完成，唯一待决项为掉线期间的危险处理，按下文实现者裁定解决。

## 玩家得到的行为

房间人数选择表示上限。人数到齐仍自动开局；房主也可在自己的连接准备完成后点击“现在开始”，让已准备的成员先玩，空位保留给后来好友。单人房间上限为 1，仍保留原单人入口；想稍后加好友时选择 2～4 人并提前开始。晚加入不重置已铺平台、委托、海域事件、商店、敌人或终局进度。

新玩家只能取得从未占用的空位，得到初始装备和初始角色数值，出生在自己的初始平台位置，不补发加入前的金币、鱼骨或委托个人收益。其空位在加入前没有可见角色，不被攻击、不参与碰撞、救援、人数门槛或全员失败判断。首次实际参与发生在统一确认帧。

已经加入的玩家掉线后保留席位、个人钱包、背包、装备和实际位置。自己的钓线断开，不恢复合钓资格；未确认的本地操作清空，重连不会自动重买、再次复活或再次扣建造材料。重连成功后读取当前权威状态，并继续使用已有的交易回执编号。

掉线期间采用以下实现者默认值，并非用户明确确认：角色继续留在世界中，停止主动移动/挥钩/游泳；已发生的击退继续走完，落水伤害、敌人攻击、倒地计时和正常耐力恢复继续。队友仍可钩救或岸上救起该角色。重连时角色可能已被救援、受伤、倒地或死亡，必须如实呈现，不额外回岸、回血或补耐力。已提出偏好题且尚未收到回复；选择此值是为了遵守原设计的持续模拟和重连不重置个人状态，后续用户若调整则同步修改规则和测试。

断线界面提供“重新连接”按钮，连接原房间并领取原席位；同步完成前不能操作或显示成可行动。恢复凭据保存在当前客户端对象/控制器中，不显示在普通日志或游戏 HUD。关闭应用后凭据不会自动持久化；本阶段验收的是网络断开后在同一应用内恢复。凭据 API 保持可供未来的账号/本地持久层使用，不以无凭据的指定槽位代替身份校验。

房主进程退出仍结束房间，不做主机迁移、跨机器云存档或账号登录。房主应用里的本地玩家连接短暂中断时，独立服务器仍可继续。胜利/失败后拒绝全新成员加入，但已占席位可恢复查看终态；重新开始仍由房主发起，等待当前在线参与者的新局屏障，离线席位保持身份保留，回来时接入当前局。

## 实现约束

帧同步核心仍是纯 C#，不认识钓鱼、生命值、商人或 Unity。框架只提供固定预留名单中的连接重新绑定、非零帧快照同步和有界追帧。房间层负责验证恢复凭据、空位分配与用户提示；游戏层负责角色是否出现、掉线后的行为和人数判定；Unity 仅提交命令并展示确认态。

沿用固定名单和已有 Activate / Deactivate / Rebind 成员事件。房间开局时预留容量内的全部稳定身份；未使用席位不绑定虚构网络连接。第一批成员在首帧 Activate；中途绑定只允许已停用席位，在同步完成后用 Rebind 严格增加控制权版本。旧连接、旧控制权、旧局号的输入一律不能影响新连接。

框架构造器默认保持“绑定覆盖名单”的旧约束；新增显式选项允许未绑定的初始非活跃席位。ClientSession 默认仍只接受第零帧初态；房间恢复客户端显式选择允许非零帧的已确认快照。现有协议消息格式无须装入玩法内容。

## 在线同步流程与边界

1. 新连接先完成房间协议校验。新入房领取未占用槽位；恢复请求必须匹配房间 ID、槽位及随机 128 位以上凭据。已在线席位不允许凭据抢占，未被服务器确认掉线时提示稍后重试。失败加入只影响申请者。
2. 等待旧成员停用帧确认后，服务器在 K 帧捕获完整 checkpoint，为此连接保存独立的快照字节、摘要、起始帧和发送偏移。所有商店时钟、鱼和敌人进度、装备及交易回执都包含其中。旧玩家的模拟继续前进。
3. 同步中的新连接不参与全房间发送背压，也不产生玩家输入。服务器按原分块协议发送 K 帧快照，同时为该连接保存 K+1 之后的确认帧；快照及追帧都有独立上限，不建立无限历史。
4. 新客户端恢复快照并校验摘要后发 Ready。服务器发送对应 Start，然后按帧序补齐缓存的确认帧；新连接确认执行进度追上当前帧且待补队列为空后，才进入正常广播和流控，并通过下一统一 Rebind 帧启用席位。客户端确认自身已活跃后才采样新输入，固定帧时钟从接入后的确认进度开始。同步连接的快照、Start 和补帧直接使用其独立队列，不进入可能阻塞旧玩家的共享发送队列。
5. 上限初值沿用会话 MaxFutureFrames（128 帧）和 PrepareTimeout（10 秒），消息/字节预算沿用 SessionOptions。同步太慢、追帧超限或传输断开时只撤销该连接的绑定并清理缓存，房间继续，用户可显式重试。队列接近容量时逐次发送，不要求一轮塞下整份快照或全部追帧。
6. 已进入正常在线状态后仍沿用现有确认帧流量控制与传输断线检测，不把本功能当成公网可靠性验证。新连接同步中的 Ready、重复 Join/Ack 及控制消息必须幂等，不重建库存或重复激活。

首次入房在成员激活后才成为永久保留席位；此前 Welcome 丢失或同步失败，释放临时席位，避免没有实际进入的连接永久占满房间。客户端收到 Welcome 后即保存待确认凭据供显式重试，确认激活后才公开已入场凭据并允许输入。服务器若已激活则恢复原身份；若尚未激活且席位仍空闲，允许原申请重试；新申请可以占用该空位并替换旧凭据，待确认凭据也不能进入终态房间。这样即使服务器已确认入场而客户端尚未收到该帧，也不会丢失恢复入口。框架暴露连接是否仍被绑定，房间层据此关闭被限额淘汰的同步连接，不积累无界失败事件。

通过新连接的自然隔离和 Rebind generation 防止旧帧污染，不为掉线时尚未确认的动作补放到新帧。服务器已确认的购买保留物品和回执；未确认的动作不会由重连接口重新排队。正常在线成员自己的请求队列不因别人加入而重置。

重开局先阻止新入房/恢复进入当前屏障，固定当时在线成员名单并通知下一局号。屏障期间有人断开仍按现有明确失败处理，不让部分队伍开始；完成后接受离线保留席位恢复到新局。新一局已在线成员正常初始化，离线/空位的角色保持未出场，等待接入时取得该新局的初始角色状态。上一局资源不跨局保留。

## 游戏和表现接入

新增明确的未出场标记（建议 WaitingToJoin，默认 false 以兼容现有测试/快照构造 API），不能复用 Unavailable 混淆“从未进场”和“已进场但掉线”。初始未活跃席位同时不可操作；成员激活后清除未出场标记。游戏流程逐项排除未出场角色：角色与水中伤害、敌人寻敌、碰撞、钩救/岸上救援、全员失败、终局所需人数及只读表现。已进场掉线角色保留世界互动，自己的输入仍被禁用。

普通鱼、食人鱼和宝箱的掉线断钩、主钓交接及最终分配沿用现有规则；重连不恢复钓线。终局合钩人数沿用可在线参与人数规则，单人提前开始的 4 人上限房间不能被未入房空位要求四人完成。所有不可行动/购物判定仍使用确认态。胜利和失败都冻结世界与奖励，同时处理成员事件；上一局保留身份若在本局结束后才回来，只查看终态，不激活本局尚未出场的身体，不改变失败结果。

界面明确区分等待加入、正在同步、在线和已断线。未出场角色不画出；已进场掉线角色可见并标明断线。加入/重连关闭本地旧面板及待发操作，恢复后的背包、生命、耐力和商店读服务器确认态。

游戏规则/状态/房间协议升至 22，状态头更新为 HISE；输入字段和地图配置保持输入 10、地图 HIMF。旧客户端和存档明确拒绝。本功能不引入旧档迁移器。

## 必须成立的验证

- 框架：预留席位、非零帧恢复、准确追帧与完整 checkpoint 相等；重绑定控制权递增；旧连接/旧 generation 输入拒绝；重复 Ready/Join 无二次启用；慢同步超限只丢申请者；失败解绑清队列；多次恢复与有界内存。
- 玩法：未出场角色不影响单人敌人/失败/终局；掉线断钩后换主和均分；水中掉线继续伤害且可救；击退不被掉线取消；自然恢复不重置；重连不重复购买、材料、掉落或敌人攻击。
- 真实 UDP：单人开局、2/4 人中途加入；2/4 人断开后恢复同一席位；保持个人数据和全世界状态，最终所有在线端完整 checkpoint 一致；错误凭据、已在线席位、不同地图和旧局请求拒绝。
- 原生客户端：显式启用的开发验收经正常输入赚取/消耗资源，实际断开 UDP、从 UI 同一入口恢复并继续钓鱼，另有四人晚加入流程；显示原位置和状态，查看同步/断线反馈。验收组件不进入发布构建。
- Unity Editor 全套、开发/发布严格构建、当前全仓库回归。仅报告实际退出成功的测试，限定本机 UDP，不宣称互联网和主机迁移已完成。

## 实现者裁定与未承诺范围

人数未满时的手动开始、只保留从未占用空位给新成员、房间存活期间永久保留已出场掉线席位、同应用内保存恢复凭据、同步限额、掉线角色持续危险和新的 UI 文案是实现者初值，并非用户逐项确认。选择这些初值是为了先把现有玩法状态恢复约束变成可操作闭环；改变开局/凭据持久化/危险策略时要更新设计和验收。

Boss/可上岸鱼的上岸行为、商人航行、账号系统和应用退出后的自动身份恢复均不借本任务扩展；已有通用存档恢复能力继续独立存在。
