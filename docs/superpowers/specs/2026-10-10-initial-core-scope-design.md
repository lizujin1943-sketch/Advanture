# 初版核心范围：先把一整条同步流程跑通

日期：2026-10-10  
状态：阶段 A 已实现并在 macOS 验证，Windows 验证待执行；B～E 尚未实现。见 [阶段 A 实现说明](../../stage-a-implementation.md)。  
适用目标：供自己的多个游戏复用的纯 C# 帧同步框架。

本文决定先做什么。[总体方案](2026-10-10-deterministic-frame-sync-design.md)保留完整目标；有阶段差异时，以本文的初版范围为准。

各模块内部怎样实现，见[独立帧同步框架技术方案](2026-10-10-frame-sync-core-design.md)。本文维护范围与运行阶段，不重复维护另一份算法细节。

## 1. 初版做到什么程度

初版完成后，应能在不启动 Unity 的情况下：

1. 启动一个服务器模块与 1～4 个客户端，参与者在开局前加入并准备好。
2. 各端使用同一初始状态；服务器确认输入，客户端预测、发现差异后回滚。
3. 在延迟、丢包、乱序下，最终计算结果仍然相同。
4. 保存一份确认状态，关闭进程后重新读取并开局。
5. 用两种不同的输入和状态模型运行，核心不用为某个例子改代码。
6. 从同进程内存通信切换到多个进程的自研 UDP 通信。

初版先允许开局前加入；运行中接入新玩家、掉线后接回旧位置，放到后续阶段。房主正常退出仍保存后关房。

“先跑起来”分成几次可验证的小成果：先内存运行，再有预测回滚，再接真实网络。不是等所有模块完成后才第一次启动，也不是把所有后续能力都提前实现。

## 2. 初版的八个核心模块

这里的模块按职责划分，不要求每个模块都建成一个独立代码包。通信库与同步核心的依赖边界必须独立。

| 核心模块 | 初版真正实现的内容 | 为什么现在就需要 |
| --- | --- | --- |
| 1. 游戏接入与模拟驱动 | 创建隔离实例；固定步长推进；由游戏解释自己的输入和状态 | 决定框架是否能换游戏、换引擎 |
| 2. 帧时间与输入记录 | 逻辑帧号、固定顺序、输入截止时间、重复与迟到处理、有限历史 | 所有同步和重算都建立在这份记录上 |
| 3. 服务器确认 | 收集输入、按规则补齐缺失、确定最终帧、执行参考模拟并广播 | 建立所有端共同使用的最终结果 |
| 4. 客户端预测与回滚 | 预测未知输入；比较最终输入；恢复旧状态重算；区分预测事件与确认事件 | 后加会影响状态、事件与输入的组织，不能只留空接口 |
| 5. 状态快照与基础存读档 | 捕获、恢复、编码、摘要比较；保存确认状态；新会话读档开局 | 回滚、存档、后续加入与重连共用这套基础 |
| 6. 房间与参与者 | 开局前连接、版本检查、初始状态分发、准备与开始、确定帧的停用、关闭 | 后续成员变化依赖稳定身份和统一的生效时机 |
| 7. 通信与消息格式 | 可替换收发接口；内存通信、故障测试网络、自研可靠 UDP 基础实现 | 同步不绑定网络，且初版最终能在不同进程间联机 |
| 8. 重放、校验与运行工具 | 控制台启动、两种简单模拟、记录最终输入、比较状态、导出错误 | 证明“真的同步正确”，而不是仅仅能收发消息 |

### 2.1 游戏接入与模拟驱动

游戏提供“向前计算一帧”“取状态副本”“恢复状态”“编码输入和状态”等方法。核心只调用这些方法，不出现移动、攻击、角色或背包类型。

初版测试使用简单整数运算。通用定点数、物理、随机工具库可以按需求后补；核心从第一天就要求接入模拟具有确定性，即相同起点和输入得到相同结果。

### 2.2 帧时间与输入记录

帧号、输入提交后不可修改、固定参与者顺序以及成员事件顺序，现在就定下来。迟到输入拒绝，缺失输入按游戏规则补齐，不临时搬到下一帧。

所有历史和未来输入都有数量与字节上限。缓冲区满后明确等待或报错，不靠无限积累让例子暂时跑通。

### 2.3 服务器确认

服务器每帧形成不可修改的最终输入记录，并实际运行游戏规则。不能初版只做输入转发，后续要存档或发状态时才另加一套权威计算流程。

房主自己的客户端也走同一输入通道，不直接改服务器状态。服务器与客户端共享代码，使用不同状态对象。

### 2.4 客户端预测与回滚

初版先用简单预测策略：未知输入默认使用游戏提供的中性输入。预测提前量固定，预测帧数有上限；自适应调节以后再做。

真正实现“已到 104 帧，发现第 100 帧不同 → 恢复第 99 帧 → 重算 100～104”，并与直接执行最终输入的结果比较。

事件现在就包含运行编号、帧号和帧内序号，并区分预测与确认。初版输出到测试记录即可，动画平滑和复杂特效修正以后接入。重算不能再次提交已经确认的外部操作。

### 2.5 状态快照与基础存读档

快照同时包含游戏状态，以及成员表、输入预测历史等框架状态。先用完整复制，不先做增量快照或压缩。

初版状态恢复接受一个明确帧号，不只能恢复“刚开局”的状态。必须用测试证明：恢复任意一个保留的确认检查点，再执行后续最终输入，能到达同样结果。

基础文件存档包括格式版本、实际保存帧、状态数据和完整性校验。只存服务器确认状态，先写临时文件、成功后替换，写失败保留旧档。读档建立新会话，旧包不能继续生效。

初版只需要一个指定保存位置、当前格式读写、明确错误和旧档保护；多存档界面、云存档、自动备份管理和复杂旧版转换后做。

### 2.6 房间与参与者

初版流程：连接 → 检查版本 → 分配合法参与者身份 → 分发初始状态 → 各端确认准备好 → 开始 → 关闭。

初始状态可以来自新建游戏或文件读档。先在开局前传完状态并验证一致，再开始计帧，不要求状态传输与运行中的游戏并行。

参与者编号、房间位置、位置控制权更新编号和临时连接编号分别记录。测试环境由宿主分配与校验身份，不把 Steam 账号或网络地址直接当作游戏对象编号。

成员加入、停用、重绑定在核心中统一表达为“指定帧生效的成员事件”。初版实际使用开局激活、运行中断线停用；重绑定的状态转换通过核心测试验证，完整的重连网络流程后做。

开局后新加入请求明确返回“本阶段不支持”。断线不会直接在网络回调中删除游戏对象；由服务器安排停用事件，游戏按自己的规则处理。

### 2.7 通信与消息格式

初版分两步：先内存与可复现故障网络，让同步流程跑通；再用同一接口接自研 UDP 和真实多进程测试。

同步消息现在就写明种类、版本、运行编号、目标帧与长度限制。通用通信接口只认识连接、字节和交付要求，不认识玩家输入。

UDP 基础实现至少包括连接、确认与重发、去重、顺序交付、分片重组、独立通道、接收额度、发送节奏与基础拥塞退让。这里“接收额度”限制对方能放多少数据，“拥塞退让”表示网络堵时减速；它们不是可以完全省略的性能优化。

初版可采用[可靠 UDP 方案](2026-10-10-reliable-udp-design.md)中简单且有上限的算法，不做复杂调参、自适应带宽优化或跨网络地址迁移。原生网络阶段在本机及受控局域网验证，平台公网通信后续接入。

大消息分片与内存上限现在就实现，避免以后要传状态时重写消息格式。状态可以开局前分块传完；运行中传状态的调度、取消与历史保留流程后做。

### 2.8 重放、校验与运行工具

使用控制台程序启动服务器和客户端，不等待 Unity 界面。提供最小日志：确认到哪帧、预测到哪帧、哪里回滚、哪帧结果不同、队列与状态占用多少内存。

保存初始状态与最终输入，能重新运行同一段过程。发现不同步先导出问题帧，不先做复杂调试面板。

两个测试模拟使用不同输入与状态结构，均留在测试或示例工程中。核心可以独立构建；删除示例不影响核心和它自己的测试。

## 3. 哪些能力必须现在落地，哪些只留接入位置

仅写一个空接口不能证明以后能接入。会影响正确性的基础现在做出来，完整使用流程按阶段补齐。

| 将来要加的能力 | 初版必须实际完成 | 后续再加的部分 |
| --- | --- | --- |
| 中途加入 | 完整状态编码／恢复；后续输入重放；成员事件；大消息分块；开局前状态分发 | 运行中发送状态、追赶服务器、额外历史保留、激活协调、失败重试 |
| 掉线重连 | 稳定参与者身份；连接与控制权分离；状态可恢复；拒绝旧包；核心重绑定规则 | 重新认证、保留期管理、网络恢复进度、自动找回控制权 |
| 正式存档功能完善 | 当前格式基础读写；版本字段；确认状态；失败保护 | 多存档、云同步、复杂迁移、自动保存策略 |
| 换游戏或引擎 | 纯 C# 核心、可替换模拟、至少两个模型验证、表现不直接改模拟 | Unity 等具体引擎接入与展示 |
| 换 Steam 通信 | 通信接口、身份接口、消息能力检查和字节预算 | 邀请、大厅、平台认证与实际通信适配 |
| 提高性能 | 明确数据归属、固定时间步、有限队列、可测量统计 | 缓冲池调优、增量状态、压缩、多线程、发送合并 |

这不是承诺未来完全不用改代码，而是让后续功能主要增加协调流程，不推翻输入格式、状态组织、游戏接入方式或传输分层。新增消息或格式变化仍明确升级版本。

## 4. 初版明确后做的内容

| 功能或优化 | 为什么可以后做 |
| --- | --- |
| 游戏进行中加入 | 依赖的恢复和成员基础已在核心，后续补并行传输与追赶流程 |
| 自动掉线重连 | 初版可明确断线并停用，后续接上恢复流程 |
| 运行中自动整状态重同步 | 初版保留恢复能力；历史不足时清楚结束该客户端会话，后续增加网络恢复协调 |
| Unity 展示与编辑器工具 | 控制台已能验证核心，不决定同步算法 |
| Steam 邀请与平台网络 | 通过适配器接入 |
| 自动更换房主 | 属于新的服务器交接协议，尚不在既定目标中，不为它提前实现选主或复制机制 |
| 输入延迟自动调节、预测策略优化 | 初版固定提前量和简单预测已经可运行 |
| 状态差量、压缩、复杂内存池 | 先以完整副本验证正确性，测量后再优化 |
| 多线程模拟、大规模人数、复杂网络调度 | 超出当前 1～4 人验证范围 |
| 完整开发工具界面与录像管理 | 命令行重放和最小诊断足够发现核心错误 |

## 5. 每一步都能运行的顺序

| 可运行阶段 | 能展示什么 | 到这里还不能声称什么 |
| --- | --- | --- |
| A：一份模拟 | 输入重放、状态捕获恢复，两种模型得到稳定结果 | 尚未联机 |
| B：内存同步 | 同一进程的服务器和 1～4 个客户端，仅用最终输入运行 | 尚未完成预测回滚或真实网络 |
| C：预测回滚 | 测试网络故意延迟／丢包，触发回滚后结果一致；事件不重复提交 | 尚未证明操作系统网络实现正确 |
| D：基础存读档 | 保存确认状态，退出重启，用载入状态重新开局并继续计算 | 尚未完成多存档、旧版迁移或云同步 |
| E：真实网络 | 不同进程通过自研 UDP 分发初始状态、交换输入、回滚、保存后关房 | 尚未实现中途加入／重连，也未验证所有公网环境 |

存读档建立在阶段 A 的状态能力上，可靠 UDP 可以独立开发验证。表格表示每次集成后应看到的成果，不要求所有模块严格串行开发。

初版完成指 A～E 全部通过。阶段 B 或 C 跑通时就有可执行成果，但不会把它称为真实网络联机已经完成。

## 6. 初版验收与后续验证分开

初版必须有：

- 单机与 1～4 客户端、两种模拟、同进程与多进程运行入口。
- 同一录制在 Windows/macOS 运行至少 10 万帧，所有对应检查点一致。
- 预测错误、本地输入迟到、最终帧缺失、乱序和重复消息用例。
- 恢复旧检查点后重演，与最终输入基准相同。
- 开局状态一致、断线停用、旧连接输入拒绝、读档后旧包隔离。
- 基础存读档成功与失败保护，以及事件不会因重演重复执行的检查。
- 队列、状态和重组内存有上限；异常能终止并说明原因。
- 记录实际耗时与内存，但先不把“零内存分配”或特定毫秒数当成优化完成条件。

中途加入、重连、复杂存档升级的完整端到端测试，随对应功能加入。四人持续 24 小时、完整游戏性能预算与实际发行环境检查，在准备把框架用于游戏上线时完成；运行中发现的无界内存或正确性问题不因此延后处理。

本文只调整初版范围与模块顺序，没有创建实现工程，也没有执行运行或网络测试。
