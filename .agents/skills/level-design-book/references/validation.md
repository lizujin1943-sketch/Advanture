# 试玩、评审与交付

## 以证据修正设计

**[原书：Playtesting / Player persona / Research]** 试玩发现实际体验和设想的差别。设计师自己会玩不等于目标玩家能理解；玩家分类可以辅助思考，但 persona 页面只是短提纲，不能当稳定心理测量模型。

**[操作化]** 每轮记录：

1. **问题**：例如“玩家在钟楼庭院能否理解出口在上层？”
2. **条件**：关卡版本、玩家背景、人数／模式、起始装备、任务、构建／设备；哪些已控制、哪些未知。
3. **观察**：实际路线、停顿、回头、失败、决策及玩家原话。观察时避免提前告诉玩家正确解法。
4. **解释**：列出可能原因及支持／反对证据，把观察与推测分开。
5. **修改**：选择最小有效的空间、信息或规则改动；有多个原因时按风险排序。
6. **复测**：使用相同问题与可比条件，检查收益和副作用。需要新手理解时安排未见过旧版本的玩家，避免重复试玩的学习效应掩盖问题。

可选数据：完成／失败位置、到达时间、错误转向、求助、路径分布、交火与死亡热区。情绪目标还需开放式访谈；快并不总是好、探索回头也不必然失败。小样本只支持有限结论，不编造百分比或统计显著性。

若没有可执行构建或真人试玩，只能做图面审查／静态可达性分析，明确尚未验证手感、AI、战术与体验。工具通过与真人体验通过分别报告。

## 评审输出

只输出有依据、与用户目标有关的问题，每项包括：

> 位置／情境 → 观察或材料证据 → 对目标的影响 → 建议改动 → 如何验证 → 尚未知什么。

例如：

> 北庭院第一次进入时，平面图上的出口被高墙遮住，而可见大门是不可用装饰。推测新玩家会误认目标；尚无试玩证据。先让塔顶地标在入口可见，并在接近转角时暴露上行楼梯，保持装饰门与可用门的视觉区别。比较首次玩家对出口方向的描述和错误转向；同时检查新增视线是否让敌人过早射击玩家。

优先处理进程阻断、无法识别的关键交互、缺乏反制的失败与目标平台性能，再处理局部风格和细节。优先级依目标调整，不用一张固定评分表代替判断。

## 新关卡的最小交付

以下是工作模板，可删减。实际参数不足时标“假设”而非空等用户提供全部信息。

- **意图**：玩法／视角、玩家能力、设计支柱、可观察的体验目标。
- **结构**：区域节点与连接；主进程、可选内容、门控、捷径、垂直与回返。可用 Mermaid、ASCII 或标注现有图。
- **区域**：玩家做什么、看见什么、有什么取舍、入口出口和必要尺寸来源。
- **制作**：先验证哪个未知项，怎样用最小白盒实现；哪些美术必须早测，哪些可以后置。
- **测试**：每个关键目标的观察问题、验证条件与当前状态。

对局部评审不要强制这些完整交付。未经实测的时长、强度和尺寸都应标记为设计估计。

## 程序化地图：本 skill 的延伸，非本书完整教程

**[项目适配]** 原书强调体验与制作方法，不提供通用 WFC、BSP 或随机地牢实现规范。若用户要求随机地图，把设计意图转换为生成约束，再同时做结构检查与真实试玩：

- 结构：起终点可达、门锁前置无死锁、必需节点存在、单向路径不造成意外困死。
- 体验：关键场景是否能识别、路线取舍是否有意义、战斗和恢复是否成立；通过结构检查不等于好玩。
- 留下 seed、生成器版本与配置以便重现，覆盖多样本和失败样本；不要仅挑最好看的一张。

这些是软件实现建议，不应作为原书逐字要求或对未知生成器的兼容性保证。
